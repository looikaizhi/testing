# 总览：协议全景

> **本篇定位**：深度轨总纲——一页看懂协议解决什么问题、怎么解决、创新在哪，并把你引向各深度篇。

> 论文来源：abstract、ch1.3、ch4.1。事实以源码为准。

## 1. 核心问题

法币 ↔ 加密货币的 C2C 兑换需求持续增长，但现有方案依赖「平台撮合 + 资产托管 + 人工仲裁」：

> **链下支付事实无法被链上合约直接验证** —— 银行/支付平台的转账状态只存在于第三方 HTTPS 响应里，区块链无法原生访问，用户提交的截图/凭证又可伪造。于是交易安全只能建立在对中心化平台的信任上。

本文核心问题：**如何在无中介条件下，把链下支付转化为链上可验证的密码学证明？**

---

## 2. 解法：半去中心化双域架构

把系统划分为两个**失效模式完全解耦**的信任域（论文 ch3.1.4、ch4.7.2）：

```
┌──────────────────────────────────────────────────────────┐
│  去中心化域 𝒟（链上，确定性执行）                          │
│  资产托管 · 订单状态机 · 证明核验 · 风控 · 平台治理        │
│  安全性 = 区块链共识 + 合约确定性执行（依赖 T1）           │
│  → 任何单一主体都无法绕过合约代码动资产                     │
├──────────────────────────────────────────────────────────┤
│  受约束中心化域 𝒞（链下，受密码学约束）                    │
│  MPC-TLS 协同计算 · 选择性披露背书 · 账户一致性链下比对    │
│  验证服务器（VS）的可信行为被密码学严格约束（依赖 T3）     │
│  → VS 作弊在 T2 下也无法产生有效虚假证明（链上验证失败）   │
└──────────────────────────────────────────────────────────┘
```

链下用 MPC-TLS 把支付事实变成密码学证明，VS 签名后**在链上合约里被直接核验**。VS 不持有任何资产，其失效只影响可用性、不危及已托管资产。信任被压到最弱假设：「只需相信 VS 不与买方合谋伪造支付平台的 TLS 响应」。详见 [03-threat-model.md](03-threat-model.md)。

---

## 3. 四层架构

| 层 | 职责 | 代码包 |
|---|---|---|
| 链上合约层 | 托管、订单状态机、证明核验、风控、保证金 | [`contracts`](../../../tlsn-extension/packages/contracts/) |
| 链下证明层 | 浏览器扩展（证明器）+ 验证服务器 VS | [`extension`](../../../tlsn-extension/packages/extension/) + [`verifier`](../../../tlsn-extension/packages/verifier/) + [`plugin-sdk`](../../../tlsn-extension/packages/plugin-sdk/) |
| 支付平台对接层 | 支付宝/Wise 的 HTTPS 接口，**无需改造** | — |
| 前端交互层 | 买方/商家 Web 界面，不持私钥 | [`web`](../../../tlsn-extension/packages/web/) |

系统支持 **CRYPTO/FIAT 双向产品**（镜像结构），通过可扩展验证器接口接入支付宝与 Wise。各包职责见 [reference/code-map.md](../reference/code-map.md)。

## 4. 两大创新（预告）

### 创新① 订单绑定哈希 H_bind
把链下 TLS 证明与链上特定订单 + 收付款账户**密码学绑定**：验证服务器签名摘要里嵌入 `H_bind`（15 字段 keccak256），任何参数篡改 → 重建哈希不符 → 签名恢复地址不在白名单 → 拒绝。**从根本上阻断跨订单复用与参数篡改**，无需额外时序约束。详见 [04 §6.2](04-protocol-design.md)。

### 创新② 半去中心化双域架构
「链上去中心化执行 + 链下受约束公证计算」：在当前全去中心化 zkTLS 时延仍过高（消费级设备数十分钟）的条件下，实现**信任最小化与可部署性的平衡**。架构预留未来集成 zkTLS 的接口，性能达标即可平滑迁移到全去中心化。详见 [03-threat-model.md §4](03-threat-model.md)。

> 💡 这也解释了**账户身份校验为何设计在链下**（VS 的 accountCheck）：当前无法在不泄露隐私下于链上验证身份，链上的账户校验入口预留给未来完全去中心化阶段。见 [04 §7](04-protocol-design.md)。

## 5. 三属性兼得（vs 现有方案）

论文表 2-2：本方案是四类主流路线中，**唯一在支持法币兑换前提下同时实现三属性**的方案：

| 属性 | 中心化交易所 | P2P OTC | 链上 DEX+预言机 | **本文方案** |
|---|:---:|:---:|:---:|:---:|
| 支持法币兑换 | ✓ | ✓ | ✗ | **✓** |
| 资产托管去信任 | ✗ | ✗ | ✓ | **✓** |
| 支付证明密码学可验证 | ✗ | ✗ | N/A | **✓** |
| 账户标识链上隐私 | ✗ | ✗ | N/A | **✓** |

代价：引入对验证服务器的弱信任 + 当前单节点部署的有限抗单点故障能力——半去中心化的固有工程权衡。

## 6. 关键实测结论（预告）

- 单笔完整换汇链上成本 ≈ **\$0.13**（Arbitrum One 均值档）。
- 端到端时延：支付宝 5.94 s（理想）/ 17.44 s（宽带）；Wise 9.74 s / 24.02 s。
- 合约测试 **实跑 336 passing / 0 失败**（12 套件，`hardhat test`）。

详见 [06-evaluation.md](06-evaluation.md)。
